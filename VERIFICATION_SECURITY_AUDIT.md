# Account verification security audit

## Evidence and scope

The audit starts at eRental 3.0 main `116d4ae`. The supplied verification export contains the November review function, role grants, constraints, indexes, policies, triggers and private bucket configuration. The foundation migration establishes administrator membership and its default-deny access. The milestone 3 audit, integration plan and test results and the 3.0 handoff describe earlier checks and gaps. The browser and PostgreSQL suites use synthetic identities. The nine PostgreSQL tests passed on the unmodified main checkout against its previous proposal.

The project owner reports that production still uses the original function. Only public browser settings were bound here. There was no linked Supabase project, SQL connection, management access, designated staging target or test accounts. The cloud browser URL also contained a query string, which the app correctly rejects. Current hosted definitions, ACLs, Security Advisor output, native Auth and Storage behavior and migration history could not be compared in this workspace. The export establishes the recorded implementation. Deployment requires fresh evidence from the intended target. ## Findings and dispositions

| Area and severity | Recorded behavior and impact | Disposition |
| --- | --- | --- |
| Competing decisions · High | The exported RPC selects the submission without a lock, checks pending in memory and writes by ID. One approved or rejected decision could overwrite another, leaving the user's badge inconsistent with the recorded outcome. | Fix in the versioned migration. Serialize access to the submission before reading its actionable status. Reject any subsequent decision on a terminal request. |
| Approval eligibility · High | The exported approval branch sets the badge from the submission kind without checking the current profile. Account type or business name can change between submission and review. | Lock the current applicant profile during approval. Require the specific identity/individual or business/business pair and a usable business name. Preserve the existing invalidation trigger on later identity edits. |
| Uncertain admin response · Medium | The 3.0 review dialog offered refresh after an uncertain RPC result, but dismissal could expose the old pending queue again. | Reconcile on dismissal as well as the explicit refresh action. A fresh queue determines whether the item is still available for review. The RPC remains authoritative across tabs and reviewers. |
| Administrator RPC access · High impact if misconfigured | The recorded RPC returns void, has a fixed empty search path and is executable by authenticated users. The membership check uses the server's authenticated user ID. The foundation revokes direct client privileges on admin membership and enables RLS with no client policy. | Retain the role probe, server-side membership check and restricted function ACL. Examine owner, effective privileges, PUBLIC/inherited grants and role memberships during preflight. No administrator identities are seeded. |
| Preview validation · Medium | The admin preview previously trusted the declared content type and size. A stored file with a PNG content type and mismatching bytes could reach the browser preview. | Validate the file signature before creating a preview URL, and require an explicit entry in the four-type allowlist. The browser fixture covers denial and URL cleanup. This check recognizes supported file formats and leaves full content inspection to the reviewer. |
| Document access · High impact if misconfigured | The recorded 5 MiB private bucket accepts JPEG, PNG, WebP and PDF. Policies allow insert in an applicant's folder and read by that applicant or an administrator. No verification policy permits client overwrite or deletion. | Preserve the private bucket. Test policy metadata locally and cover browser authorization failure, canonical owner paths, legacy filenames, explicit authenticated downloads and temporary URL cleanup. Require real Storage acceptance before rollout. |
| Badge and submission integrity · High impact if misconfigured | The applicant can insert five submission columns. The server sets decision fields. Public profile selection includes verification kind/date; client update grants are limited to display name, business name, account type and avatar. The invalidation trigger clears both badge fields on a protected identity change. | Retain column grants, RLS and triggers. Read both protected profile fields for badges. A terminal request remains part of history after badge invalidation. Confirm actual project grants and trigger enablement. |
| Evidence retention and identity matching · Operational | A private upload can outlive a failed submission. Account names are read from the current profile. There is no stored, immutable snapshot of the name on an earlier submission. | Accept within the existing product contract. Review the document against the current identity. Use a new submission when identity evidence is ambiguous. Only an authorized operator following the project's retention policy should handle orphan cleanup. |

## Review transaction

The RPC derives the actor from Auth and checks administrator membership before processing the submission. Once the submission lock is acquired, a waiter sees the committed status or receives a transaction error at stricter isolation. It can never replace a committed terminal decision. An approval checks eligibility under the applicant's profile lock. The decision and protected badge writes use the same transaction. Failure rolls back both. Rejection requires a reason and leaves protected profile fields alone. There is no public data or document operation in the review RPC.

The approval takes a `FOR NO KEY UPDATE` profile lock. It serializes ordinary identity edits while allowing the key-share locks used by reviewer foreign keys. Independent PostgreSQL sessions confirmed both behaviors. A forced failure during the badge write also rolled back the submission decision. [Database tests](tests/postgres/verification.test.js) · [Results](VERIFICATION_SECURITY_TEST_RESULTS.md)

The recorded profile update triggers only modify the current profile tuple. They do not take a submission lock. The preparation trigger reads the profile on a new submission and the partial unique index limits each applicant to one pending request. A profile edit that precedes the approval lock is visible to the eligibility check. A protected edit that follows approval executes the badge invalidation logic.

Supabase recommends an empty search path with schema-qualified objects for privileged functions and explicit execution grants because PostgreSQL normally grants EXECUTE to PUBLIC on function creation. The application needs authenticated execution of this particular RPC. Keeping its server-side authorization and checking privileges during replacement preserves that intended API. The verification diagnostic and local role tests provide evidence about the checked-in contract. A hosted Security Advisor rerun and the staging matrix remain release gates.

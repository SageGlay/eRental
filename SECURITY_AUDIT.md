# Supabase security audit

Initial review on 18 November 2026. The verification findings below include the November hardening work. Inputs are [the foundation migration](supabase/migrations/20261102083451_foundation_profiles_categories_listings_photos.sql), [the project owner's verification export](supabase/contracts/verification.json), frontend callers and the advisories supplied for this milestone. The export is the last inspectable function definition. The cloud proxy rejected the hosted connection and no live metadata connection was available. The [read-only metadata query](supabase/diagnostics/milestone_3_security_contract.sql) obtains current definitions, effective role privileges, RLS policies, constraints and bucket settings in the existing project's SQL Editor.

Whether a separate consumer intentionally uses it remains unknown. A definer can bypass table RLS and therefore needs its own scope check. No live disclosure was observed. | High-priority metadata review before the pilot. Confirm fixed search path, safe qualification, visible/eligible listing scope and date-only output. Inspect every definer, including trigger helpers, overloads, inherited/PUBLIC privileges, owners, search path and actor checks. Preserve necessary EXECUTE for proven callers. For report decisions require admin, and for simulated payment require eligible renter, correct booking and transaction-level duplicate prevention. ## Verification review hardening

The recorded review function allowed a second administrator to overwrite a committed decision. It also allowed approval after the applicant changed to an ineligible account type. Migration `20261119184647` locks the submission before checking its status. An approval then locks the applicant profile and checks the current account type and, for a business, a nonblank business name. Both writes commit together. The database tests also confirm that a later protected profile edit clears both badge fields. [Migration](supabase/migrations/20261119184647_harden_verification_review.sql) · [Findings and residual risks](VERIFICATION_SECURITY_AUDIT.md)

The RPC keeps its signature, owner, privileges and empty search path. It derives the reviewer from Auth and checks administrator membership. Tests exercised concurrent PostgreSQL sessions, forced rollback, role grants and private object metadata. The browser uses a private download, checks the file signature before preview and reloads the queue after an uncertain decision. [Test results](VERIFICATION_SECURITY_TEST_RESULTS.md)

## Staging, deployment and rollback

The staging operator must capture current definitions and effective privileges, compare migration history, run the single-version dry run, and execute VS01–VS12 using synthetic files and five designated accounts. The hosted Security Advisor and real Auth and Storage checks are outstanding. Production rollout requires successful staging evidence and separate, explicit authorization. [Deployment and acceptance procedure](VERIFICATION_SECURITY_DEPLOYMENT.md)

Rehearse the guarded inverse in staging. It restores the recorded function and leaves committed review records and badges intact. Pause reviews before rollback because the restored function permits competing decisions. Verify the restored catalog before reconciling its migration-history row.

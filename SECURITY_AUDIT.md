## Verification proposal review

The [forward SQL](supabase/proposals/20261118_serialize_verification_reviews.sql) lives under proposals so routine migration commands leave it pending. It preserves the original `public.review_verification(uuid,text,text)` function identity, argument names/default, void return, owner and effective grants. It keeps `SECURITY DEFINER`, the empty `search_path`, the `is_admin()` check, approve/reject actions and the existing rejection note rules. The guard refuses to create a missing RPC or replace it when the checked client EXECUTE privileges differ.

The function locks the submission first and reads its latest status under that lock. Only a pending submission can be finalized. An approval then locks the associated profile and checks the kind against its current account type and requires a nonblank business name for business approval. The existing trigger clears the badge when protected identity details change after approval. Blank business names now fail approval even if an older profile row allowed blank text. Rejection of a mismatched request remains possible. Stable name/document snapshots between submission, review and approval would require a separate workflow decision. A name edit before approval can still leave a document needing human comparison if the account type and business-name check pass.

`npm run test:db` started **PostgreSQL 17.12** in an isolated container with no network or published port. It builds only the relevant recorded tables, grants, indexes, triggers, policies and functions, with fixture adapters for Auth identity and Storage key folders. Separate sessions observed actual lock waits. The first decision survived in both orderings. A committed profile type edit blocked approval and a later identity edit cleared the approved badge. The suite also checked nonblank business names, note constraints, denied review calls, private metadata isolation, unchanged function attributes, refusal to create a missing RPC, and rollback. Supabase Auth email, JWT validation, HTTP Storage behavior, other deployed triggers and other hosted roles were outside the local fixture.

## Staging, deployment and rollback

1. Run `npm run test:db` from the repository on a Docker-capable machine. It creates its own temporary PostgreSQL container. It takes no Supabase URL, password or database connection string.
2. In the **approved staging project's** SQL Editor run the metadata diagnostic. Compare the deployed `review_verification`, `is_admin`, table constraints, trigger functions, grants, role memberships and Storage policies with the recorded export. Save the exact live pre-change function definition and metadata privately. Stop if function identity, privilege posture, lock ordering or related triggers differ until the proposal has been reconciled.
3. Apply the reviewed forward proposal only to the designated staging database. Run live cases V01–V05 and validate owner/admin/unrelated roles with newly staged sample evidence. Capture approval/rejection from two independent authorized sessions in both orders. Confirm the second final decision fails and no conflicting badge remains. Make a profile edit race with approval in each order and verify type/business eligibility plus post-approval badge clearing. Record the actual staged SQL version and outcomes.
4. In staging, apply the [rollback](supabase/proposals/20261118_serialize_verification_reviews.rollback.sql) only if its saved definition matches the exact pre-change definition. Otherwise restore the saved pre-change definition with a reviewed `CREATE OR REPLACE FUNCTION`. Recheck function attributes and SQL role access. Rollback restores code and reintroduces the old race. It does not reverse committed reviews or badge changes. Pause concurrent reviews if reverting the fix.
5. Obtain explicit production authorization before any hosted production function change. Back up current metadata and carry the verified staging procedure into the approved change window. Compare metadata again after application and run only approved fixture checks. Escalate incorrect committed decisions separately under project procedures. No hosted SQL was applied in this milestone.
